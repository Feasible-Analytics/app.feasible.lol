Ad blockers block analytics by hostname. Serving the script and the events endpoint from your own domain is the only reliable way around that, and it costs you two proxy rules.

It is also better for your visitors: the request goes to a host they already trust and reuses a connection their browser has open.

What to proxy

  • The script — a static file, cacheable. It is served at /js/script.js, or at your site's own /js/fs-<token>.js.
  • The events endpoint — POST /api/event, never cached. Proxy the whole prefix rather than the exact path, so the no-script pixel at /api/event/pixel.gif is covered too.

Caddy

example.com {
    handle /stats/js/* {
        uri strip_prefix /stats
        reverse_proxy https://feasible.lol {
            header_up Host feasible.lol
        }
    }
    handle /stats/api/event* {
        uri strip_prefix /stats
        reverse_proxy https://feasible.lol {
            header_up Host feasible.lol
        }
    }
}

Caddy sets X-Forwarded-For itself, which is all we need.

nginx

location /stats/api/event {
    proxy_pass https://feasible.lol/api/event;
    proxy_set_header Host feasible.lol;
    proxy_set_header X-Forwarded-For $remote_addr;
}
location /stats/js/ {
    proxy_pass https://feasible.lol/js/;
    proxy_set_header Host feasible.lol;
}

Then point the script at your proxy

<script defer data-domain="example.com"
        data-api="/stats/api/event"
        src="/stats/js/script.js"></script>

data-api is not optional here. Left out, the script derives the endpoint from the origin of its own src — not the directory — so a script served from /stats/js/script.js would post to https://example.com/api/event, which is a path you are not proxying. The script loads, the requests 404, and the site looks installed.

The one thing to get right

Your proxy must pass the visitor's address on. Without it, every visitor geolocates to your data centre and shares one fingerprint — one visitor, from one country, forever — and there is no way to repair that afterwards.

We resolve the address in this order:

  1. X-Feasible-IP.
  2. CF-Connecting-IP.
  3. The nearest untrusted address in X-Forwarded-For, walking from right to left past trusted proxy hops. This remains correct when a proxy appends to a client-supplied chain.
  4. The address the connection came from.

The first three are read only when the connection address is listed in FEASIBLE_INGEST_TRUSTED_PROXIES. The default list is empty, so a directly connected visitor cannot forge the address used for their fingerprint, geolocation or IP shields. Set the variable to your load balancer or edge proxy, never to a public client range. That trusted edge must strip or overwrite client-supplied X-Feasible-IP and CF-Connecting-IP because they take precedence. It may append X-Forwarded-For; the right-to-left walk rejects a spoofed value placed before the address the edge observed.

Check one real page load before you leave it running: send an event through the proxy with X-Debug-Request: true and look at client_ip and client_ip_source in the reply. If the source says socket and the address is your server's, either the proxy is not trusted or the header is not arriving.

The address itself is used for geolocation and the visitor identifier and is then discarded. It is never written to disk and never leaves the ingestion tier — see privacy.

WordPress does this for you

The WordPress plugin proxies both routes on randomised paths under your own domain, rotates those paths on request, and forwards the visitor's address. If you run WordPress, that is less work than either block above.

Content security policy

Proxying makes this easier rather than harder: once both requests are same-origin, a strict CSP needs no analytics host in script-src or connect-src at all.
