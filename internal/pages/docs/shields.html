Two settings that decide what gets counted and what it is called, at /settings/<your domain>/shields and /settings/<your domain>/paths.

Shields — traffic you do not want counted

Blocked addresses

An address or a CIDR block. Checked in the ingestion tier, which is the only place the raw address still exists — after that it has been discarded and there is nothing left to match on.

The screen shows you the address this request resolved to, using exactly the same header precedence the event endpoint uses, with a one-click Block my own traffic. That is also a free diagnostic: if it shows a private address, your reverse proxy is not passing the visitor's address through, every visitor currently resolves to the same one, and a rule built on it would block everyone. The one-click action is hidden in that state, but the manual rule form can still add the shared address. Fix the proxy before adding it — see proxying.

Blocked countries

Two-letter ISO country codes. Worth it when a country is, for your site, entirely bot traffic.

Blocked pages

A path, or a path ending in * to block everything beneath it. Staging routes, health checks and preview builds live here.

Allowed hostnames

This one is an allow-list, not a block-list: with no entries everything is accepted, and with one or more entries anything not named is dropped. It is the answer to somebody else's site sending events with your tracker id — a copied theme, a scraper, a staging clone nobody told you about.

Thirty rules of each kind

Per site, per kind. If you are approaching that on blocked pages, a /staging* prefix rule is usually what you actually wanted.

What a shield actually does, and where you see it

It stops the event being counted, and the drop is counted rather than silent — but the two halves happen in different places, which matters if you are testing a rule with curl:

  • Blocked addresses are decided in the ingestion tier, before the response, so shield_ip comes straight back in the x-feasible-dropped header.
  • Countries, pages and hostnames are decided at the shard that holds your data, after the request has already been answered with its 202. They are counted as shield_country, shield_page and hostname_not_allowed, and they can never appear in that header. A blocked page still answers exactly like an accepted one; the event simply does not arrive in your reports.

A change takes effect within about fifteen seconds, and saving from this screen pushes it immediately.

Shields are not retroactive. They change what is collected from now on, and they do not remove what is already stored.

Path cleaning — URLs that are really one page

/users/3f2a…/settings and ten thousand siblings are one route you think in and ten thousand rows on your report. A path cleaning rule merges them:

PatternReplacementResult
^/users/[^/]+/settings$/users/:id/settingsone row instead of thousands
^/blog/([^/]+)/comments/.*$/blog/$1/commentskeeps the post, drops the comment id

A pattern is a regular expression — a real one, not a glob — and a replacement may refer back to a capture group with $1. Rules are tried in order and the first match wins; they are not chained, so a path is rewritten once. Up to 30 rules per site, and a pattern may be up to 500 characters. A pattern that will not compile is refused when you save it, naming the rule number and the pattern.

The two things that make it worth using

It is retroactive. Reports apply the current mapping at query time, so saving one fixes the history you already have and new events use the same mapping immediately. The screen tells you how many stored paths each rule moves before you save it, and again after.

New traffic keeps its original. This version stores the original path and gives reports a source-to-target mapping. Delete every rule and those retained originals come back. Older versions rewrote paths while rules were active; an original already lost that way cannot be reconstructed, so removing a rule leaves those legacy cleaned values as they are. Retaining originals for all new writes means the path dimension still contains each distinct raw path; the rule controls report grouping rather than erasing source data.

Trailing slashes

Most sites serve the same page at /about and /about/, and the two are otherwise two permanent rows on every report. There is a one-switch rule for it. It ships off rather than decided for you, because a few sites genuinely serve different content at each and silently merging those would be wrong.

Preview before you save

The preview shows exactly what saving would do and how many stored rows each merge moves. Nothing is written until you say so.
