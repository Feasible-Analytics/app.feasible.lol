A custom property is a key and a value attached to an event, so you can break a report down by something only your application knows — a plan name, a category, a variant.

feasible('Signup', {
  props: { plan: 'yearly', referred_by: 'partner' }
})

A pageview takes them under p rather than props, which is a wart of the wire format we match for compatibility:

feasible('pageview', { p: { variant: 'b' } })

The limits, and what happens at each one

  • 30 properties per event. The rest are dropped and counted as props_over_limit. Which thirty survive is not luck: names are sorted and the first thirty kept, so the same event always loses the same properties.
  • 300 bytes per name, 2,000 per value. Longer ones are cut to the limit and counted as prop_name_too_long or prop_value_too_long. The property is still stored — truncated, not rejected.
  • Strings, numbers and booleans only. An object, an array or a null is dropped and counted as prop_value_unsupported. It is as lost as a thirty-first property would be, and nothing is lost quietly: every one of these counters is kept per site, and the whole event's tally comes back on a X-Debug-Request.
  • A property name may not contain a double quote or a backslash.

Numbers are normalised, so 1 and 1.0 are one value rather than two rows that look identical and never add up.

Scope: a property of one hit, or of a whole visit

Every property has a scope, and it is worth thinking about for ten seconds when you add one.

  • Event scope — a fact about one hit. The product in an Add to cart. The file in a download.
  • Session scope — a fact about the whole visit. The A/B variant. The plan tier the visitor is signed in as.

The scope decides a denominator, which is the only reason it exists. A conversion rate filtered by an event-scoped property divides by everybody, because the property only exists on the conversion itself. Filtered by a session-scoped one it must divide by the visitors who had that value — the visitors in that variant — or the variant with fewer visitors always looks worse than it is, for arithmetic reasons that have nothing to do with your test.

A property nobody has scoped is treated as event-scoped, which is the conservative answer. The scope can be changed later: getting it wrong the first time is normal, and correcting it is one setting rather than a support ticket.

Today there is no screen or API field that sets a scope — the engine reads it, the seeded demo data sets it, and the control for it arrives with the goals interface. Until then every property behaves as event-scoped.

Do not put personal data in a property

Email addresses, names, user ids, session tokens. A property is stored and returned exactly as your site sent it, and shown on a dashboard, and we cannot un-store it for you afterwards. If you need to segment by user, send a value that identifies a group rather than a person.

The same applies to query strings. Every parameter except the seven acquisition ones — ref, source, utm_source, utm_medium, utm_campaign, utm_content, utm_term — is stripped from the stored path before anything is written, precisely because sites do put tokens and addresses in them.

Reading them back

Every property is available as a dimension in the query API, as event:props:<name>, and can be grouped by, filtered on and combined with any other filter:

{
  "site_id": "example.com",
  "metrics": ["visitors", "events"],
  "date_range": "28d",
  "dimensions": ["event:props:plan"],
  "filters": [["is", "event:name", ["Signup"]]]
}

There is no separate "custom dimensions" allowance to configure and no extra charge for using them.

In the dashboard, a property is not yet in the filter menu or the breakdown list — that arrives with the same interface work as goals. The URL grammar already understands one, so a hand-written link filters correctly and the pill renders with the property's name:

/dashboard/example.com?period=28d&f=is,event:props:plan,yearly

A property is not free, but it is not billed either

The custom event carrying it counts towards your monthly volume. The properties themselves add nothing — one event with thirty properties is one billable event.
