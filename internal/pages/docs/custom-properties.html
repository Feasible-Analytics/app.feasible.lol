A custom property is a key and a value attached to an event, so you can break a report down by something only your application knows — a plan name, a category, a variant.

window.feasible('Signup', {
  props: { plan: 'yearly', referred_by: 'partner' }
})

The limits, and what happens at each one

  • 30 properties per event. The rest are dropped and counted as props_over_limit on the ingestion health panel.
  • 300 characters per name, 2,000 per value. Longer ones are truncated and counted, not rejected.
  • Strings, numbers and booleans only. An object, an array or a null is dropped and counted as prop_value_unsupported. It is as lost as a thirty-first property, and the whole point of that panel is that nothing is lost quietly.

Do not put personal data in a property

Email addresses, names, user ids, session tokens. A property is stored as sent and shown on a dashboard, and we cannot un-store it for you afterwards. If you need to segment by user, send a value that identifies a group rather than a person.

The same applies to query strings. Every parameter except the seven acquisition ones is stripped from the stored path before anything is written, precisely because sites do put tokens and addresses in them.

Reading them back

Every property is available as a dimension in the query API and as a breakdown in the dashboard, and can be combined with any filter. There is no separate "custom dimensions" allowance to configure and no extra charge for using them.

A property is not free

The custom event carrying it counts towards your monthly volume. The properties themselves do not add to that count — one event with thirty properties is one billable event.

Aggregating a numeric property

A property that holds a number can be summed, averaged and reduced to a percentile, not just counted. The metric names are the aggregate in brackets around the property:

"metrics": ["sum(event:props:price)", "avg(event:props:price)", "p95(event:props:load_ms)"]

The aggregates are sum, avg, min, max, p50, p75, p90, p95 and p99. They combine with every filter and every breakdown, so the 95th percentile of a load time per page is one query.

The percentiles are nearest-rank: the answer is always a value somebody actually sent, never a number interpolated between two real ones. For a load time that matters — an interpolated 95th percentile is a duration no visitor experienced.

What happens when the values are not all numbers

Properties are stored as text, because a property is a filter value on a dashboard and a column that is sometimes a number and sometimes a word is a column nothing can index. So a property that holds 19.99 on most events and free on a few is a real possibility, and the honest thing to do with the word is leave it out — counting it as zero would drag an average down with nothing on the screen to say why.

That is what happens, and the response says so. Any aggregate that had to skip a value comes back with a not_numeric warning naming both counts: "measured over 412 of the 431 values of price — the other 19 are text and were left out rather than counted as zero". A property that turned out to hold no numbers at all says that too, rather than answering zero and letting you read it as a real zero.

Scope decides what a sum adds up

A property registered as event-scoped describes one hit, so a sum adds up every event that carried it. A property registered as session-scoped has one value per visit by declaration, so it is counted once per visit however many pages that visit touched. Get that the wrong way round and an order value repeated on six pageviews is summed as six orders — a number six times too large that looks perfectly reasonable. This is the whole reason a property carries a declared scope.
