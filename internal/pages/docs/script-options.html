Every option is a data- attribute on the script tag. There are no build flags and no separate script variants to choose between: one file, and the attributes decide what it does.

data-domain (required)

The site this page belongs to, exactly as registered. It is the routing key for the whole system. A page whose data-domain does not match a registered site is dropped with the reason unknown_site, which you can see on the ingestion health panel.

data-api

Send events somewhere other than the default endpoint. This is what you set when you proxy the requests through your own domain — see proxying.

data-exclude

A comma-separated list of path patterns that are never counted. * matches within a path segment and ** matches across segments, so /admin/** excludes an entire subtree. Excluded pages send nothing at all, rather than sending and being filtered later.

data-include

The inverse, for a site where most pages should not be counted. If both are present, data-exclude is applied after data-include.

data-hash

Treat the URL fragment as part of the page. Set it only if your routing genuinely uses hashes; on a normal site it turns every in-page anchor into a separate pageview.

data-manual

Stop automatic pageviews entirely and send them yourself with window.feasible('pageview'). It exists for applications whose idea of a "page" does not match the URL. Use it sparingly: a manual pageview that is missed is data nothing can recover.

data-outbound, data-file-downloads

Automatically record clicks on links that leave your site, and on links to files. Both arrive as custom events, so both count towards your monthly volume.

data-revenue

Allow revenue amounts on custom events. Amounts are stored with their currency and are never converted at write time, so a change to exchange rates cannot rewrite last quarter.

Local development

The script does nothing on localhost and on private addresses by default, so your development traffic never reaches your production numbers. Set localStorage.feasible_local = "true" in your browser console to opt one machine in while you are testing an install.

The Core Web Vitals collector

Web Vitals are measured by a second, optional script rather than by the one above, and the reason is the size budget. The main script has to fit in three kilobytes over the wire, and it already does, with about a dozen bytes to spare. Putting another four measurements in it would mean raising that ceiling for every site we serve — including the ones that never asked for Web Vitals — so the collector is its own file and its own kilobyte, loaded only where it is wanted:

<script defer data-domain="example.com" src="https://feasible.lol/js/script.js"></script>
<script defer data-vitals src="https://feasible.lol/js/vitals.js"></script>

It reports LCP, CLS, INP, TTFB and FCP as an event called Web Vitals, with one numeric property per measurement, so every one of them is a custom property you can aggregate, filter and break down by page like any other. Nothing in it reads layout: every number comes from the browser's own Performance API, which hands over measurements it has already taken rather than being asked to compute one. A script that damaged the numbers it was measuring would not be worth having.

It sends once, when the page is hidden. That is not a delay we could avoid — cumulative layout shift and interaction to next paint are not final until the visitor has stopped looking at the page, so a report sent on load would always be smaller than the truth.

data-sample

The fraction of page loads that report, between 0 and 1. It defaults to 1, every load. Web Vitals are a distribution rather than a total, so a tenth of your traffic describes the same curve — data-sample="0.1" is worth setting on a busy site. We do not do it for you, because quietly reporting a tenth of somebody's page loads without their knowing is exactly the kind of decision this product exists not to make.

The event counts towards your monthly volume like any other custom event, which is the other reason it is opt-in. At a sample of one in ten, that is one extra event per ten pageviews.
